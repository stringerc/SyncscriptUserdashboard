# CORTEX VISION — Implementation Spec

> Companion to `CORTEX_VISION.md` (the *why*). This document is the *how*:
> file-level detail, data contracts, acceptance criteria, per phase.
>
> **Grounding:** all file paths, function names, and tool identifiers below
> were verified against the codebase on 2026-11-13.

---

## 0. Conventions

- **Client state:** `persistentStore` (`src/lib/persistent-store.ts`) —
  namespaced keys, quota-safe.
- **Panels:** `openSurfacePanel(input)` — `src/lib/cortex-surfaces.ts:406`.
  Max 6 visible (`MAX_VISIBLE_PANELS`), zones defined at `:195`.
- **Execution:** `execTool(tool, args, signal)` —
  `src/components/cortex/useVisualizerVoice.ts:324` →
  `POST /api/cortex/tools/execute`.
- **Proposals:** `getCortexProactiveInitiative()` singleton —
  `src/lib/cortex-proactive-initiative.ts:188`.
- **API:** all Cortex endpoints are inline Vite middleware in
  `vite.config.ts` (~9.2k lines). New endpoints follow the existing
  pattern: `server.middlewares.use('/api/cortex/...', handler)` with
  `isAllowedOrigin` + `x-cortex-key` checks.
- **Verification gate:** `npm run verify:cortex` must stay green.

## PHASE 1 — Initiative Inbox (the visible loop)

**Goal:** proposals generated by the existing engine become visible,
actionable cards. User clicks Accept → action executes through the
existing tool path.

### 1.1 Data model — extend `ProactiveProposal`

File: `src/lib/cortex-proactive-initiative.ts`

Add fields (backward-compatible, all optional):

```ts
interface ProactiveProposal {
  // ... existing fields ...
  autonomyTier: 0 | 1 | 2;          // maps to vision tiers
  status: 'pending' | 'accepted' | 'dismissed' | 'snoozed' | 'executed' | 'failed';
  snoozedUntil?: number;
  executionResult?: { ok: boolean; summary: string; at: number };
  source: 'engine' | 'sensor' | 'llm' | 'voice';
  dedupeKey?: string;              // prevents re-proposing the same thing
}
```

Migration: `loadState()` treats missing fields as
`autonomyTier: requiresApproval ? 2 : 1`, `status: 'pending'`,
`source: 'engine'`.

### 1.2 Proposal store → evented

Add `subscribeProposals(l)` + `notify()` to the engine (same pattern as
`subscribeSurfaces` at `cortex-surfaces.ts:187`). Every mutation
(`evaluateInitiatives`, `dismissProposal`, new `acceptProposal`,
`snoozeProposal`, `markExecuted`) notifies listeners. Cap retained
proposals at 50 (already done via `slice(-50)` — keep).

New methods:

```ts
acceptProposal(id: string): Promise<{ ok: boolean; summary: string }>
snoozeProposal(id: string, untilMs: number): boolean
markExecuted(id: string, result: { ok: boolean; summary: string }): void
```

`acceptProposal` does NOT execute directly — it emits a
`cortex-initiative-accept` `CustomEvent` on `window` carrying
`{ proposal }`. Execution is owned by the voice/host layer (1.4) so the
volition governor and abort semantics stay in one place.

### 1.3 Initiative Inbox panel

New component: `src/components/cortex/CortexInitiativeInbox.tsx`

- Reads `getCortexProactiveInitiative().getActiveProposals()` +
  `subscribeProposals`.
- Renders cards grouped by urgency (high → low):
  title, summary, category chip, confidence %, tier badge
  (`AUTO` / `REVIEW` / `CONFIRM`).
- Actions per card:
  - **Accept** (tier 0/1) → `acceptProposal(id)`
  - **Review** (tier 2) → expands args preview + requires typed
    confirmation ("type ACCEPT") before `acceptProposal`
  - **Snooze** (1h / tomorrow) → `snoozeProposal`
  - **Dismiss** → existing `dismissProposal`
- Empty state: "All clear — Cortex is watching." (Restraint as UI:
  silence is a valid, calm state.)
- Registered as a surface panel kind: add `'initiative_inbox'` to the
  panel-kind union + a renderer case in `CortexSurfaceLayer.tsx`
  (alongside existing artifact/markdown renderers).

Auto-open policy: panel opens once per session when ≥1 high-urgency
proposal exists; otherwise accessible via surface command
`"open initiative inbox"` (extend `cortex-surface-commands.ts` phrase
table).

### 1.4 Executor wiring

File: `src/components/cortex/useVisualizerVoice.ts`

In the host component (`CortexVisualizerPage.tsx`), add an effect:

```ts
useEffect(() => {
  const onAccept = async (e: Event) => {
    const { proposal } = (e as CustomEvent).detail;
    const res = await execTool(proposal.suggestedTool, proposal.suggestedArgs);
    getCortexProactiveInitiative().markExecuted(proposal.id, {
      ok: !res.text.startsWith('Error'), summary: res.text.slice(0, 200),
    });
    // announce outcome through the bus so the HUD reflects it
  };
  window.addEventListener('cortex-initiative-accept', onAccept);
  return () => window.removeEventListener('cortex-initiative-accept', onAccept);
}, []);
```

Guard: if `proposal.autonomyTier === 2`, the inbox already required typed
confirmation — the event only fires post-confirmation.

### 1.5 First three proposers

Extend `evaluateInitiatives()` with options-fed signals (caller supplies
data; engine stays pure):

```ts
evaluateInitiatives({
  freeEnergy, uncommittedFileCount, freeMemMB,          // existing
  unansweredEmailCount?, staleTaskCount?,                // NEW
  nextMeetingInMin?, meetingPrepReady?,                  // NEW
  pendingInvoiceCount?, anomalousChargeCount?,           // NEW
})
```

New proposal generators (each ~20 lines, same shape as existing):

| Proposer | Trigger | Suggested tool |
|---|---|---|
| `email_triage` | `unansweredEmailCount > 3` | `cortex_gmail_draft` (new thin tool wrapping live-inbox + draft) |
| `git_checkpoint` | `uncommittedFileCount > 20` | `run_command` → `git add -A && git commit -m "cortex: checkpoint"` (tier 2) |
| `task_stale` | `staleTaskCount > 0` | `cortex_tasks` → surface stale-task panel |

### 1.6 Acceptance criteria — Phase 1

- [ ] Proposals render in a dockable panel; state survives reload
      (persistentStore).
- [ ] Accept on a tier-1 proposal executes the suggested tool and the
      card flips to `executed` with the result summary.
- [ ] Tier-2 proposals cannot execute without typed confirmation.
- [ ] Dismiss/snooze persist; snoozed proposals resurface after
      `snoozedUntil`.
- [ ] `npm run verify:cortex` green; no new console errors.
- [ ] Unit test: engine proposal lifecycle
      (pending→accepted→executed / dismissed / snoozed).

**Effort:** M (2–4 days). **Risk:** low — additive only.

## PHASE 2 — Sensor bus + cadence

**Goal:** evaluation stops being LLM-initiated; it runs on a schedule
and on events.

### 2.1 `/api/cortex/initiative/sense`

New middleware in `vite.config.ts`. Returns one JSON snapshot:

```json
{
  "ts": 1730000000000,
  "ambient": { "frontmostApp": "Xcode", "windowTitle": "..." },
  "vigilance": { "...": "existing /vigilance/status payload" },
  "git": { "uncommitted": 42, "branch": "main", "ahead": 3 },
  "gmail": { "unanswered": 4, "urgent": 1 },
  "tasks": { "open": 17, "stale": 3, "dueToday": 2 },
  "calendar": { "nextMeetingInMin": 25, "meetingsToday": 4 }
}
```

Implementation notes:
- Reuse existing handlers' logic — extract shared functions rather than
  duplicating osascript calls (the 4s ambient poll already exists; cache
  its last result with a 30s TTL — also fixes the perf issue from the
  audit).
- `git` via `execFile` (not `execSync`) — audit finding.
- Gmail/tasks/calendar read from the same stores the existing endpoints
  use; if a source is unavailable, return `null` and the proposer skips.

### 2.2 Client poller

`src/lib/cortex-initiative-sensor.ts` (new):

- `startInitiativeSensor(onSnapshot)` — polls `/sense` every 5 min,
  pauses when `document.visibilityState === 'hidden'` (audit finding:
  gate ambient work behind visibility).
- Event triggers: dispatches `cortex-initiative-evaluate` on
  `visibilitychange → visible`, on `cortex-signal-bus` state transitions
  to `idle`, and on new-email signals if a push channel exists.
- Calls `evaluateInitiatives(snapshot)` and `saveState()`.

### 2.3 Voice surface

`useVisualizerVoice.ts` — extend `cortex_proactive_initiative` tool args
with `action: 'list' | 'accept_top' | 'dismiss'` so "what needs my
attention?" / "approve the top one" work hands-free.

### 2.4 Acceptance criteria — Phase 2

- [ ] `/api/cortex/initiative/sense` returns all sections; missing
      sources degrade to `null`, never 500.
- [ ] Proposals appear within 5 min of a qualifying condition without
      any LLM turn.
- [ ] No osascript/git spawn while tab hidden (verify via Activity
      Monitor or server log timestamps).
- [ ] Voice: "what needs my attention" lists pending proposals;
      "approve the top one" executes tier ≤1.

**Effort:** M. **Depends on:** Phase 1. **Risk:** medium — new endpoint
must reuse `isAllowedOrigin` + key check (audit: endpoints currently
wide open — apply the gate here from day one).

## PHASE 3 — Trust Ladder v1

**Goal:** per-domain autonomy graduation with a legible audit trail.

### 3.1 Data model — `src/lib/cortex-trust-ledger.ts` (new)

```ts
interface TrustEntry {
  domain: string;              // e.g. 'git_checkpoint', 'email_draft'
  tier: 0 | 1 | 2;
  cleanExecutes: number;       // consecutive successes
  totalExecutes: number;
  lastFailure?: { at: number; reason: string };
  graduatedAt?: number;
  revokedAt?: number;
}
```

Store: `persistentStore` key `cortex:trust:v1`. Singleton
`getCortexTrustLedger()`.

### 3.2 Graduation rules (v1 — conservative)

- Tier 2 actions **never** auto-graduate in v1 (invariant).
- Tier 1 → auto (tier 0 behavior for that domain) after
  `cleanExecutes >= 10` AND `totalExecutes >= 15` AND no failure in last
  30 days.
- Any failure resets `cleanExecutes` to 0 and logs to ledger.
- User can revoke per-domain from the Inbox UI ("Autonomy" section) or
  by voice ("stop auto-committing").

### 3.3 Enforcement point

`acceptProposal` consults the ledger: if the proposal's domain has
graduated, skip the card entirely and execute silently — *but still write
the audit entry* (legibility invariant). Surfaces an undo toast for 30s.

### 3.4 Audit trail UI

Inbox panel gains an "Activity" tab: chronological ledger entries —
what ran, when, tier at time of execution, outcome. This is the
radical-legibility primitive (vision §6.4) in its minimal form.

### 3.5 Acceptance criteria — Phase 3

- [ ] Ledger persists; graduation math unit-tested (boundary at 10/15).
- [ ] A graduated domain executes without a card; undo toast works.
- [ ] Failure demotes cleanly; revocation is instant and auditable.
- [ ] Activity tab shows every autonomous action with tier + outcome.

**Effort:** M–L. **Depends on:** Phase 2 (needs steady proposal flow).
**Risk:** medium — this is the first phase touching real autonomy;
server-side policy enforcement (Phase 3.6) should land *before* broad
rollout.

### 3.6 Server-side policy (prerequisite for production autonomy)

Move the tier check into `/api/cortex/tools/execute` middleware: the
server validates `autonomyTier` + ledger state (synced via a signed
client attestation or server-held ledger copy) before running
Tier-1-auto domains. Until this exists, Phase 3 ships behind a
`cortex.trust.enabled` flag defaulting OFF.

## PHASE 4 — Goal model + drift + forecasting

**Goal:** Cortex holds a model of what you're *becoming*, not just what
you're doing.

### 4.1 Goal store — `src/lib/cortex-goals.ts` (extends existing `useGoals`)

```ts
interface LifeGoal {
  id: string; title: string;
  horizon: 'week' | 'month' | 'quarter' | 'year' | 'life';
  status: 'active' | 'paused' | 'achieved' | 'abandoned';
  declaredAt: number; targetDate?: number;
  signals: string[];          // observable proxies (commits/wk, calls made…)
  driftScore?: number;        // computed
}
```

Seed from existing goals contexts; allow voice declaration
("Cortex, my goal this quarter is X").

### 4.2 Drift detection

Weekly evaluator (extends sensor bus): for each active goal, compute a
drift score from its signals vs. trailing baseline. `driftScore > 0.6`
for 2 consecutive weeks → proposal:
*"You've drifted from 'ship Cortex Phase 1' — 3 weeks, zero commits.
Recommit, restructure, or drop it?"* — tier 1, `cortex_goals` tool.

### 4.3 Self-forecasting (v1 = simple)

Baseline-rate predictions only: "you skip gym Thursdays 70% of the
time" computed from history; proposal pre-commits a countermeasure
(reschedule, accountability ping). No ML — frequency tables over your
own data. Honest about confidence.

### 4.4 Acceptance criteria — Phase 4

- [ ] Goals declarable by voice + UI; persisted.
- [ ] Drift proposal fires on synthetic drift in tests.
- [ ] Forecast proposals cite their own sample size ("based on 14
      Thursdays").
- [ ] No goal auto-modified — proposals only; user decides.

**Effort:** L. **Risk:** high-ish — wrong drift scores erode trust
faster than missing features. Ship with conservative thresholds +
"why am I seeing this" explainability on every proposal.

## PHASE 5 — Somatic, attention firewall, diplomacy (research-grade)

These are R&D spikes, not committed features. Each gets a time-boxed
prototype and a kill criterion.

### 5.1 Somatic inputs
- Spike: Apple HealthKit export / wearable webhook → `wellness` section
  in `/sense`. Proposer: "HRV down 20% + 4 consecutive late nights →
  propose moving tomorrow's hard block."
- Kill criterion: signal quality too noisy to beat calendar-only
  heuristics after 2 weeks of data.

### 5.2 Attention firewall
- Score every inbound item (email/notification/event) against active
  goals; default-deny non-vital interruptions.
- Build on existing notification surfaces; measure interrupt rate
  before/after. This is the highest-trust-risk feature — needs Tier-2
  discipline on *withholding* information too.

### 5.3 Cortex-to-Cortex protocol (long horizon)
- Spec-only in this phase: message envelope, mutual authentication,
  negotiation transcript format, human-in-the-loop escrow for
  commitments. Prototype: two local instances negotiating a meeting
  slot.
- Blocked on: Phase 3 trust ledger (agents must be accountable before
  they can negotiate).

## PHASE 6 — Frontier R&D (uncharted)

Not scheduled. Each item is a research question with an explicit
"what would count as evidence" note. See `CORTEX_VISION.md` §6 for the
full primitive list. Suggested first spikes:

| Spike | Question | Evidence of life |
|---|---|---|
| Temporal self | Can the system answer "what did past-me know that present-me forgot" usefully? | Users report changed decisions |
| Forked self | Does simulated-alternate-life reporting change real choices? | A/B on proposal acceptance |
| Machine mortality | Does giving Cortex a persistent self-narrative across model swaps change user trust? | Retention across model upgrade |
| Restraint metric | Can we measure "calibrated silence" — proposals *not* made that would've been noise? | Dismiss-rate ↓ over time |

## Cross-cutting requirements (all phases)

1. **Server-side policy enforcement** before any Tier-1-auto rollout
   (Phase 3.6). Client-side governor is UX, not security.
2. **Audit ledger** — every autonomous action writes an immutable-ish
   entry (append-only JSONL under `.cache/cortex_audit/`).
3. **Nudge budget** — max N proactive interruptions/day, user-tunable;
   Cortex can propose *fewer* nudges as trust grows (restraint metric).
4. **Explainability** — every proposal carries `why`: which signals,
   which thresholds, what data it used. No opaque proposals.
5. **verify:cortex green** at every merge; new endpoints get origin
   checks from day one.

## Suggested build order

```
Phase 1 (Inbox) ──→ Phase 2 (Sensor bus) ──→ Phase 3 (Trust Ladder)
                                                │
Phase 4 (Goals) ────────────────────────────────┤
                                                ▼
                              Phase 5 spikes (somatic/firewall/diplomacy)
                                                │
                                                ▼
                              Phase 6 frontier R&D (as capacity allows)
```

Phase 1 is deliberately small: it makes the *existing* engine visible.
Everything else is additive on top of a loop that already half-exists.
